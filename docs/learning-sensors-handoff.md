# 학습 센서 구현과 Claude 인수인계 — 2026-11-05

## 사용자 결정과 목적

최상위 목표는 AGENTS.md를 따른다. 좋은 교사를 만나는 운에 따른 격차를 줄이기 위해 효과적인 영어 수업을 발견·검증·개별수업으로 제공한다. 기존 학생 스탯을 유지하거나 공개하는 것이 목적이 아니다. 학생의 학습 성과, 필요한 시간·연습량, 도움 필요 정도, 지속성을 개선하는 데 필요한 관측을 우선한다.

수집·연결·분석은 교사·부모의 추가 기록 없이 자동화한다. 교사에게는 실행 가능한 추천을 제공하고 **배정·변경은 교사가 승인/수정/건너뛰기를 선택**한다. 기존에 승인한 계획 안에서의 실행·복습과 새 계획의 무단 배정을 구분한다. 이번 변경은 채점·등급·복습·배정 규칙을 바꾸지 않는다.

## 운영 적용 상태와 순서

**이번 채팅에서는 운영 DB 실행·환경 변경·커밋·푸시·배포하지 않는다. 로컬 구현/합성 검증 단계다.**

1. 선행 DB 041, 047/060, 074, 090 및 최신 프로젝트 스키마 확인. 088은 선택 사항.
2. 승인 후 `097_learning_sensors.sql` 적용. `097_check.sql` 읽기 전용 검사에서 전 칸 true 확인.
3. 운영 역할과 테스트 학생으로 잘못된 열쇠·다른 학원·닫힌 기능·기록/조회 권한 확인. 합성 DB 테스트가 실제 Supabase 권한 확인을 대신하지 않는다.
4. 배포 환경에 `VITE_LEARNING_SENSORS_ENABLED=true`를 명시하고 빌드/배포. 일반 빌드는 누락 또는 다른 값이면 신규 클라이언트 수집 없음. 승인된 Vercel 운영 빌드는 build:vercel 래퍼가 누락 시 true를 주입하므로 중지는 명시적 false로 한다. 기존 학습과 채점은 그대로 동작한다. 플래그만 켜고 DB가 없으면 missing_migration으로 수집을 중단한다. 일반 연결/권한 오류는 missing으로 숨기지 않는다.
5. `/admin/system` 수집 상태에서 경로별 도착 확인. 기존 서버 근거는 신규 센서 비활성 상태에서도 RPC 적용 후 조회 가능하다.

## 앞으로 만드는 기능의 센서 계약

개발자는 기능 구현 시 아래를 함께 설계한다. 교사에게 별도 입력을 요구하는 체크리스트가 아니다.

1. 학습 목표/재료 ID(같은 철자 다른 뜻 구분), 블록·문항·규칙 버전, 실제 실행 모드(group/solo/homework/preview)를 연결한다. 기성 ID가 없으면 임의 연결로 채우지 말고 미해결로 표시한다.
2. 서버가 발급한 run ID/불변 버전을 지향하고, 계획된 배치와 실제 제공한 순서·내용을 구분한다.
3. 어떤 단서(그림·뜻·소리·보기·힌트·정답)를 언제 제공했는지 기록한다. 제시·첫 응답·재시도·도움 후 새 문항·시간 경과 후 확인을 분리한다.
4. 공통 훅/API를 실제 플레이어에만 연결한다. 미리보기·자동 테스트·합성 계정을 운영 학습 근거로 섞지 않는다. 자동 테스트에서 센서 flag는 기본 off.
5. 정오/난도/학생/학원/자료 범위는 클라이언트가 선언한 값으로 신뢰하지 않는다. 기존 서버 채점 재사용 또는 서버 검증이 필요하다.
6. 게임은 실제 제시한 단어·라운드·단서를 기록하고 게임 점수와 후속 개인 확인을 구분한다. 인쇄·외부 링크는 관측 범위를 명시한다.
7. 추천은 생성→노출→승인/수정/건너뛰기→실제 배정→후속 평가를 같은 추천 ID로 연결한다. 승인율은 학습 효과가 아니다. 교사 최종 결정권을 보존한다.
8. 데이터 누락·재전송·역순·중복·중단 복귀·다른 학생/학원·닫힌 기능을 검증한다. 이벤트/기술 장애를 학생의 실패로 해석하지 않는다.
9. 효과 분석을 위해 사전 상태·평가 문항·평가 대상 분모를 정하고, 비교/실험은 교사가 승인한 범위 안에서 실행한다. 근거 부족이면 기존 경로 유지와 확인 추천을 제공한다.
